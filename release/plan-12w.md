# 发布与 12 周判据（v1.0.1）

> 目的：让「要不要继续投入」变成一个能算的问题，而不是感觉。
> 判据写在最前面，指标和检查点跟着，最后写不达标时怎么处置。

---

## 一、判据（12 周，从首发日算）

**达标 = 满足任意一条**

| 指标 | 门槛 | 从哪看 |
|---|---|---|
| GitHub stars | ≥ 150 | 仓库首页 |
| 周活用户 | ≥ 100 | 本地无遥测，用「Release 下载数 / 每周新增 issue 里提到实际在用」估算 |

**不达标 = 12 周后两条都没到**，按下文第四节处理，不延期、不改判据。

不把「star 数好看」当唯一目标：本项目无计费，star 只是传播度；周活才是「有没有人真的在用」。
两者都没有，说明这套做法对目标读者不成立。

---

## 二、首发三步（三天内）

| 天 | 动作 | 完成标志 |
|---|---|---|
| D1 | 发 GitHub Release 1.0.1（正文用 `release/1.0.1.md`）；仓库 README 保持现状 | Release 页面可见 1.0.1，含两个高危的说明 |
| D1 | 知乎首帖 | `release/posts/zhihu-01.md` 发布，带四组对照表 |
| D2 | 小红书首帖（7 图） | `release/posts/xiaohongshu-01.md` 发布，正文含「GitHub 搜 sjiwj/jy」 |
| D3 | B站视频 / 专栏 | `release/posts/bilibili-01.md` 按分镜录制，3 分 10 秒 |

三渠道不同稿：知乎吃数据、小红书吃痛点、B站吃节奏。**同一篇稿子三处发，等于只发了一处。**

---

## 三、每周检查点（每 7 天，10 分钟）

只记四个数，写进 `issues/weekly.md` 的表格里：

```
周次 | stars | Release 下载数 | 新增 issue | 本周修了几个
W1
W2
...
W12
```

另外每周只回答一个问题：**这周有没有人贴出他自己的数据/复现？**
有 → 那是唯一值得优先回的东西（比 star 重要）。
没有 → 继续按 issue 流水线清 bug。

---

## 四、不达标时的处置（先写死，避免到时候找理由）

12 周到点、两条都没到：

1. **停止扩展入口**。九个入口不再加第十个，也不再做新功能。
2. **砍到两个入口**：只保留「质检」和「文风」——这两个是纯本地、不依赖长上下文、单次调用就能验证价值的。
3. **写作流水线转成文档**：8 拍 / 章纲规范 / 硬线指标全部写成方法论文档，代码退回到「能跑就行」。
4. 把结论写进 `issues/retro-12w.md`：哪条判据没到、当时怎么估的、错在哪。

理由：这个项目的核心资产是**方法**（章纲分场、硬线、上游优先），不是界面。方法不成立时，界面做得再多也只是自娱。

---

## 五、达标之后也别急

即使到了 150 stars，也不立刻扩功能。先做两件事：

1. 把 3 个以上真实用户的复现数据收进 `issues/`（他们的书、他们的模型、他们的数字）；
2. 用这些数据回头改硬线阈值——现在的 5 条硬线（句长 / 段长 / 最长段 ≤100 / 对话 ≥0.25 / 破折号 0）是**一本样书**上定的，样本量为 1。

样本量为 1 的阈值，写进 README 时要标明是「初值」，不能当普适标准卖。

---

## 六、这份文件的验收

- 判据可算：150 stars / 100 周活，有明确来源与时间窗；
- 处置可执行：砍到两个入口、方法论文档化，不是「再看看」；
- 检查点可落盘：`issues/weekly.md` 一张表，四个数。

不达标就按第四节做，不需要再讨论一次。
